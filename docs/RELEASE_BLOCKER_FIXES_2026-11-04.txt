1. ROOT CAUSES AND FIXES

A1 — expired scoped pushes
Root cause: scoped publication validated its authorization outside the scoped
try/catch. A scoped lock was 'pushing' while its parent draft remained 'pending'.
The queue failure callback only handled parent status 'pushing', so an expired
ticket, revoked permission or worker failure could leave the scope held forever.

Fix:
- Validation is inside the scoped cleanup lifecycle.
- ShopYourVibeEditing::failScopePush locks the draft row and checks ticket ID and
  scope revision before releasing a hold. It leaves desired order, approval and
  remote checkpoints intact. Older failures cannot release replacement attempts.
- PushShopYourVibe::failed recognizes scoped tickets, including serialized jobs.
- Scoped execution uses a shared atomic lock lasting 900 seconds, longer than the
  840-second worker timeout and shorter than the 960-second queue reservation.
- acquireScope can recover an expired hold only when no scoped worker owns that
  execution lock. It probes the lock API: Cache::has cannot inspect atomic locks
  stored separately by array/database cache drivers.
- The execution lock is keyed by collection scope, so the same remote collection
  represented under different parent drafts cannot execute overlapping scoped pushes.
- Expired-ticket, permission and timeout cleanup preserves the approved revision;
  an authorized editor can reacquire and issue a fresh ticket without discarding it.

Evidence: original audit reproduction left the hold 'pushing' after 841 seconds.
FinalPredeploymentAuditTest now asserts no new remote call, a released hold,
retained approved_revision and successful reacquisition. It delivers the old failure
callback after creating a replacement ticket and asserts that replacement survives.
ScopedPublicationRecoveryTest covers a simulated killed worker: at 841 seconds the
live execution lease still blocks reacquisition; at 901 it recovers without losing
approval. Permission-revoked tickets send no mutation and release their own hold.
The corresponding forced two-process MySQL replacement races also passed.

A2 — asynchronous Shopify reorder jobs
Root cause: scoped sorting discarded collectionReorderProducts job IDs, issued
dependent chunks without waiting and treated immediate order readback as sufficient.
It bypassed the existing generic remote_jobs/checkpoint confirmation infrastructure.

Fix:
- Scoped sorting now uses the same remote_jobs map, trackJob, waitForJob and
  checkpointCollection helpers as the generic publication path.
- Before an HTTP reorder request, it stores an 'unconfirmed:<uuid>' intent marker.
  A returned Shopify job ID replaces it durably before waiting for completion.
- Each chunk completes and its collection checkpoint is read before another chunk
  is sent. Resume first waits for an already stored job instead of blindly resending.
- Remote checkpoint updates merge only the affected collection under a row lock,
  retaining other collections' newer checkpoints and snapshots.
- The final exact real-product order is read back; only then does a fenced database
  transaction mark sorting published and release the scoped hold.
- Authorization is checked before every new mutation and again before publishing
  the final local state. The per-request callback is always cleared on exit.
- Edits and discard of the collection are blocked while its remote job remains
  unresolved. Unrelated collection scopes remain editable. Other parent drafts
  cannot publish this remote collection while one draft has an outstanding job.

Lost responses require an explicit distinction:
- Known job ID: normal retry or worker restart resumes confirmation automatically.
- Response lost before the ID is persisted: the uncertainty marker remains. No
  second reorder, discard or false success is allowed. A matching local draft or
  a single coincidentally matching remote read does not prove an async job ended.
  An operator must establish the remote job outcome/provenance before repairing
  that checkpoint. This change intentionally provides no unsafe 'assume failed'
  button or automatic replay. It does not invent an idempotency guarantee that
  Shopify collectionReorderProducts does not supply.

Evidence: original audit recorded synced with jobDone=false, no VibeJob queries
and empty remote_jobs. The corrected reproduction instead stays pending and
stores the job, then finishes after confirmation. DeferredScopedReorderFake holds
the actual order until its job completes; a 501-product reverse order exercises
multiple dependent chunks and throws if a later chunk is sent early. Exact final
order and published status are asserted. A lost accepted response is retried and
the fake sees exactly one reorder, with no publication. Discard is rejected and
an independent loaded collection can still be sorted.

A3 — generic engraved inventory bypass
Root cause: specialized engraved services checked flags, but generic tracking,
on-hand sync, product updates and other writers called shared HTTP gateways with
no engraved participation check. A queued generic job could bypass disabled flags.

Fix:
- Added EngravedBeadMutationGuard at ShopifyApiClient GraphQL/REST and the separate
  ShopifyGraphqlClient gateway. The GraphQL throttle loop rechecks before retries.
- Generic ProductInventorySyncService also checks its reliable local product and
  variant identities before resolving remote inventory identities.
- Participation is resolved from product tags/configuration, product/variant/item
  GIDs or numeric IDs, handles, and ALL discovered family-member mappings, including
  inactive mappings and mappings whose catalogue tags have changed. It does not
  require an active/approved family. Newly created tagged bead inputs are protected.
- Nested mutation inputs and literal GIDs are inspected. REST product/variant/item
  path identities and numeric inventory-item inputs are included.
- Identity types remain distinct: Product/777 must not be blocked merely because
  an engraved InventoryItem/777 exists. No mutable identity result is cached.
- Mutation is rejected unless both required flags (and the existing overall feature
  flag) permit it. Read queries continue to work. A rejected mutation is never sent
  to Shopify and the caller retains a failed/dirty/pending result.

Existing writer trace:
Generic inventory sync / old InventorySyncJob / retry: ProductInventorySyncService
  -> ShopifyApiClient, guarded before tracking/policy/on-hand writes.
Manual stock / purchase-order receipt movements: ShopifyInventoryAdjustmentService
  -> ShopifyApiClient, guarded at HTTP boundary in addition to specialized guards.
Bulk tracking: local variant intent -> InventorySyncJob -> guarded generic service.
Product updates: ProductShopifyUpdater -> guarded GraphQL or REST client.
Launch: existing ProductLaunchService blocker plus the guarded HTTP boundary.
Specialized bead order/sellability/tracking/fulfillment/reconciliation paths retain
  their existing EngravedBeadWriteGuard. They are not activated by this work.
Background Shopify sync uses the separately guarded ShopifyGraphqlClient.

Evidence: original audit recorded inventoryItemUpdate for an inactive family with
both flags false. The same generic-service fixture now records ZERO mutations,
reports a failed variant and leaves dirty intent. The guard matrix tests each
disabled combination (false/false, false/true, true/false), product/variant/item
and inactive-mapping identity, eight mutation forms, REST, literal IDs and both
actual HTTP gateways. Undiscovered tagged products are protected. Unrelated stack
identities, including a numeric cross-resource ID collision, remain allowed.
The existing engraved and ordinary stack suites provide additional path coverage.

A4 — incomplete full collection snapshots
Root cause: collection() validated individual nodes/cursors but did not require a
valid count, reject duplicate product IDs or compare unique fetched count with the
reported collection count. Its result fed snapshots and publication confirmation.

Fix:
- Full collection reads and membership-only reads share strict count, uniqueness,
  completion and bounded stable-read helpers.
- Counts must be nonnegative JSON integers and remain identical across pages.
  Missing, string, negative or conflicting counts fail closed.
- Duplicate product IDs, missing/repeated cursors and incomplete terminal results
  are rejected. Full reads have an explicit page bound as well.
- Detected changing reads are retried once FROM THE BEGINNING. Persistent churn or
  incomplete results preserve the last confirmed data and leave work unconfirmed.
- Publication uses this full reader, so partial results cannot justify success.

Evidence: original reader accepted one product with productsCount=3 and a terminal
page. The same input now throws. Tests cover duplicate IDs, malformed counts, zero
count with nonempty products, truncated pages, missing terminal cursors, 100/101/
200/201 boundaries and a count change between pages. They assert retry starts at
after=null, and failed refresh preserves both confirmed snapshot and desired state.
Existing publication-confirmation tests run alongside these regressions.
Shopify does not offer a cross-request database transaction: these checks detect
inconsistent responses rather than claiming to freeze all external store changes.

2. STACK REMOTE-DISABLE RECOVERY

The additional risk was reproduced BEFORE its fix. The new regression expected a
retryable exception after a fake Shopify rejection; the old InventorySyncJob returned
normally. Output: storage/logs/blocker-stack-before.txt.

Implemented without changing component quantities, reservation math, fulfillment,
consumption, cancellation or restock calculations:
- InventorySyncJob throws on failed push results, with five attempts and bounded
  backoff [60,120,300,900]. Approval batches are not marked applied on failed pushes.
- Failed local inventory intent remains dirty. Automatic stack disable/restore also
  records 'stack_sellability_pending' in the existing batch field before enqueue.
- A five-minute scheduler scan requeues ONLY that explicit automatic intent. It
  does not publish arbitrary dirty/manual inventory edits. Legacy serialized
  automatic stack pushes adopt the pending marker when processed by new code.
- Queue uniqueness bounds repeated scheduling. Each execution reloads current variants.
- Before clearing stack dirty intent, the service reads Shopify back and verifies
  tracking and intended on-hand quantity. Synthetic stack disables use the intended
  stack quantity, not a stale previous on-hand snapshot. Physical components are
  not modified by this synthetic stack readback correction.
- Dirty false/confirmed variants are not requeued. An unrelated manual dirty stack
  edit is explicitly tested not to be queued by this retry scan.

The fake failure/recovery regression asserts: first disable fails and throws; local
state stays disabled/dirty; an identical next event has no new local changes; the
durable scan nevertheless queues a retry; later fake Shopify success confirms
tracked=true/on_hand=0; only then do dirty/error state clear. No live disable ran.

Other default jobs include 3600s image/report operations, 1800s inventory/sync work,
and 300s webhook handlers. The old 90s visibility timeout was unsafe with two workers.

normally; unknown outcomes require operational reconciliation. No authenticated real

successful two-user manual SYV test remains valid evidence of the normal workflow.
