EACH FINDING: ROOT CAUSE, CORRECTION AND VERIFIED OUTCOME

1. UNKNOWN/NULL COMPONENT STOCK: FIXED, P0

Root cause: generic complementary-product sellability intentionally accepts
unknown inventory. Stack enforcement reused it and could restore a stack to
untracked inventory when component tracking/quantity was null.

Change: app/Services/StackBundleSellabilityService.php:487 adds a stack-specific
eligibility check requiring known tracking and, for tracked components, a known
quantity. It retains explicit untracked semantics and existing component-unit
checks. General complementary sellability and stack consumption formulas remain
unchanged.

Original reproductions: tracking=null/quantity=null and tracking=true/quantity=null
both now retain tracked zero stack inventory. The old automatic restoration is
no longer reproduced. Known stock recovery and explicit untracked components
continue through the existing tests. A failed component refresh remains a hold.

2. UNCONFIRMED ASYNC REORDER: PARENT GAP FIXED, SCOPED QUARANTINE PRESERVED, P1

Root cause: parent publication stored a remote job only after receiving the
mutation response. Losing an accepted response could leave no uncertainty record;
a matching order could then be mistaken for completed asynchronous work.

Changes: app/Services/ShopYourVibeWorkflow.php:1088,1110 persists unconfirmed:<uuid>
before parent remove/reorder requests. Known job IDs are retained and polled.
The existing waitForJob guard still refuses unconfirmed markers. Scoped ordering
retains its existing pre-dispatch marker and execution lock.

Original reproduction: fake accepts a reorder, exposes the target order but loses
the response while its job remains pending. Both the initial and retried parent
stay failed/pending, the marker survives and exactly one reorder was sent. A
matching Shopify snapshot does not clear uncertainty. Existing delayed known-job,
dependent-chunk, revoked-permission and scoped recovery tests remain passing.

Additional independently reproduced gateway defect: ShopifyApiClient itself could
retry a THROTTLED mutation response containing execution evidence. The former
four-attempt path was reproduced before editing; app/Services/ShopifyApiClient.php:81
now stops rather than replaying a mutation when a throttled response contains
data or an actual execution cost. Queries and proven pre-execution throttles
retain their bounded retry behavior. The new fake-response regression verifies
one request and an explicit uncertain outcome.

3. PARENT CONCURRENCY/EXPIRED LEASE: FIXED, P1

Root cause: a 180-second Cache::add marker could expire within an 840-second job.
Ticket validation alone did not fence the old owner; get/put and get/forget
renewal/release were not atomic ownership operations.

Changes: app/Services/ShopYourVibeWorkflow.php:2274 uses an owner-aware 900-second
cache lock, exceeding the 840-second job budget. A held token is checked rather
than revived. Before-mutation hooks, remote-job persistence and collection/final
checkpoints verify ownership. Release uses the owner token. operationRunning
recognizes both legacy markers and current atomic locks; a short atomic probe
works with the supported cache drivers without relying on protected APIs.

MySQL reproduction after correction: workerB cannot enter workerA's live lease;
after forced expiry/takeover, workerA's real push is rejected before another
Shopify call. A cannot release B's lease; B can release its own lease. Existing
scoped execution locks remain separate and effective. Shared cache and worker
termination budgets remain mandatory production prerequisites.

4. LAYOUT PUBLICATION WITH HELD SORTING: FIXED, P1

Root cause: the parent deliberately skipped unpublished explicit sorts, then
compared final Shopify state against those unsent desired orders.

Change: app/Services/ShopYourVibeWorkflow.php:1167 builds a confirmation projection
using held collections' confirmed baselines, verifies the layout and actual
published collections, then merges the held desired orders back as pending.
It does not publish or approve those orders.

Original reproduction: card rename now succeeds remotely without a false failure.
Draft remains pending with no error; the held desired order differs from its
unchanged snapshot, and zero unapproved reorder calls are sent. Existing scoped
collection isolation, membership, approval and publication cases still pass.

5. TERMINAL PARENT FAILURE/ABANDONMENT: FIXED, P1

Root cause: failed() returned while the dead worker's marker existed. Later marker
expiry did not transition the ticketed pushing draft, and the narrow legacy
discard exception correctly refused to discard it.

Changes: app/Jobs/PushShopYourVibe.php:61 records terminal failure on the matching
ticket while a lease remains. app/Services/ShopYourVibeEditing.php:454 adds
recoverParent, called under a row lock during acquire and by the actual
syv-parent-recovery scheduler callback. Once no worker lease exists and the ticket
ended/expired, it increments the revision, archives the failed ticket and marks
the parent failed/pending. Desired state, snapshots and remote checkpoints remain
intact. It sends no Shopify request and does not expand the legacy discard escape.

Original reproduction: after the dead marker expires, actual scheduled recovery
releases the local pushing state without discarding work. MySQL checks defer
cleanup while the lease is held, then recover the same draft with identical
desired/snapshot values. Old tickets are fenced by the revision change.

6. APPROVED BUNDLE QUANTITY: FIXED, P0

Root cause: approval wrote current_on_hand_quantity, but bundle publication chose
inventory_qty and confirmed that old target before marking the request applied.

Changes: app/Services/InventoryAdjustmentApprovalService.php:93 keeps requested
values in approval items until remote confirmation. It marks dirty intent and
records its generation instead of replacing confirmed local quantities.
app/Services/ProductInventorySyncService.php:219 selects the approval item's exact
tracking/quantity target for approved batches, including bundles. Automatic

Original reproduction: a bundle at four approved to nine now sends nine with

Approval alone leaves confirmed local on-hand at four. Manual component/stack
consumption formulas and tracking representations were not redefined.

Stock confirmation changes:

9. MISSED/COALESCED INVENTORY EVENTS: FIXED GAP; DAILY FALLBACK RETAINED, P1

Original coalescing setup now leaves a durable version and queues reconciliation.

Additional independently reproduced daily edge: a failed bulk component read

NEW SCHEMA AND DEPLOYMENT PREREQUISITES

The code introduces two migrations, tested on SQLite and disposable MySQL:
  database/migrations/2026_11_04_200000_create_inventory_write_intents.php
    inventory_write_intents plus variants.inventory_write_version;
  database/migrations/2026_11_04_201000_create_inventory_reconciliations.php
    per-item durable version/processed_version reconciliation state.
These were NOT applied to production. Rollout must back up, apply these migrations
and coordinate workers before new code consumes the schema. Do not run old workers
against a partially switched lock/intent protocol.

The release remains HOLD until an operator verifies all of the following:

1. Shared locks: every scheduler/SYV/inventory server uses the same supported
   atomic database/Redis cache and namespace. A per-host file/array cache is
   unacceptable for multi-server exclusion. Verify scheduler health and timing.

2. Queue consumers: configure and verify workers for inventory-events,
   inventory-receipts and inventory-reconciliation as well as inventory-sync,
   shop-your-vibe, syv-notifications and existing launch/ledger/default queues.
   Worker termination/restart and supervisor stop budgets must respect declared
   job timeouts and stay below reservation visibility. Do not lower the long
   default lease to accelerate short-job recovery.
   If default long jobs use Redis/Beanstalk/SQS instead of the reviewed database
   connection, verify their visibility explicitly: a 90-second default cannot
   protect a 14400-second job. The new database routes do not configure that backend.

3. Coordinated transition: drain/stop old writers before starting new ones. New
   atomic locks recognize legacy markers but cannot retrofit fencing into an
   old binary after its short marker expires. Old serialized queued jobs retain
   their previous routing; inspect/drain them deliberately. Do not shorten
   reservations or automatically replay uncertain stock mutations to clear a queue.

4. Legacy pending data: inventory approvals already queued before this change lack
   the new verified generation metadata. They are not silently grandfathered into
   a write. Inventory API credentials/actor permission checks also intentionally
   reject unauthenticated legacy human stock pushes. Review original approval,
   prior execution/audit and current stock before a selected reviewer queues new
   work. Keep all pending records; do not fabricate confirmation or discard them.

5. Uncertain outcomes: review inventory_write_intents status started, receipt
   manual_review/started markers, parent unconfirmed remote jobs, expired tickets
   and notification sending/uncertain records. These remain deliberate holds.
   Reconcile against provider job/adjustment/message evidence and recorded
   references. A matching quantity/order or elapsed time alone is insufficient
   evidence of a specific earlier asynchronous operation completing. Do not delete
   or reimport affected records as a workaround; do not clear a started marker and
   retry a delta. No automated uncertainty-clearing command was introduced.

6. Stock location contract: verify the configured location and actual catalog
   location distribution. Tracked absolute counts spanning multiple locations
   are now held for location-specific review. The patch does not invent an
   allocation formula. If production needs those writes, this release is NO-GO
   until a separately approved per-location workflow is implemented and verified.

7. Permissions: ensure legitimate requesters/reviewers/operators are active and
   have inventory.update through the intended role/direct permission. Status-only
   staff must remain unable to approve/push stock. Recheck selected reviewers and
   production access before requeueing held legacy work.

8. Engraved beads: retain existing inventory-write and store-contract gates OFF.
   Eligibility being enabled is not permission to mutate inventory. Verify cached
   configuration and worker versions during a later authorized rollout, but do not
   activate writes as part of this release. Actual bead stock-pool, location,
   reservation and checkout activation validation remains a separate task.

FINAL DECISION

All documented confirmed code blockers have corrections and regression evidence.
Scoped quarantine, receipt atomic claims, two-person approval, manual idempotency
and CAS remain effective in the tests and forced MySQL interleavings. The additional
gateway replay, aggregate-location and stale daily-read paths were reproduced and
closed as part of independent verification.

This is CONDITIONAL GO for code review and an authorized controlled rollout only.
It is not an unconditional production GO. No production host, cached configuration,
supervisor topology, legacy queue contents or real stock-location contract was
inspected. The operational prerequisites above are unresolved until an authorized
operator supplies evidence. Until then, the release remains HOLD. Any failed
prerequisite or required unsupported multi-location stock flow makes it NO-GO.
