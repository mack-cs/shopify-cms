1. UNKNOWN OR NULL COMPONENT INVENTORY ALLOWING STACK SELLABILITY

Classification: CONFIRMED DEFECT. Existing production-capable stack inventory.
Locations: app/Services/ProductSellabilityService.php:38-45;
app/Services/StackBundleSellabilityService.php:335-357,460-505,696-708;
app/Services/ProductInventorySyncService.php:284-310.

Path: stack enforcement loads components -> firstComponentIssue -> general local
sellability -> isVariantSellable. Both unknown tracking and a tracked variant
with unknown quantity return true. The required-component-quantity check also
skips a null quantity. With no other component issue, restoreSellable changes the
stack to untracked inventory, clears its finite quantity and marks it dirty for
Shopify publication. This is how ordinary available stacks are represented;
that representation itself is not established as defective by this finding.

Safeguards: missing products, inactive products, known zero/insufficient quantities
and failed Shopify refreshes are checked. Enforcement has a per-draft cache lock.
None turns a successful read containing unknown inventory into known component
availability. Generic refresh can persist missing tracked/quantity fields as null.

Reproduction: create a stack currently tracked at zero with an associated active
component; set component quantity null with (a) tracking null, (b) tracking true;
run the real enforceForAffectedStacks. Both cases restore the stack to untracked
inventory and mark it dirty. Two diagnostic cases passed. No stack accounting
or product tracking code was changed to obtain this result.

Impact: a stack can become purchasable without evidence that its physical
components exist. Deployment blocker: YES.
Smallest correction: require known adequate inventory for tracked/unknown
physical stack components at the stack eligibility boundary. Preserve explicitly
untracked component semantics and the existing component consumption model;
do not globally change complementary-product eligibility without separate tests.
Keep a refresh failure or incomplete read unresolved and retry/reconcile it.
Coverage: existing ShopifyInventoryWebhookStackSellabilityTest covers known
zero, known recovery, status changes, and persistent failed pushes. It did not
cover these null states. New diagnostic: "null component stock" datasets.

2. UNCONFIRMED SHOPIFY ASYNCHRONOUS REORDER RECOVERY

Classification: INTENTIONAL SAFETY for scoped publication; CONFIRMED DEFECT in
the parent/legacy path. Locations: app/Services/ShopYourVibeWorkflow.php:932,1103-1104,
1239-1285,1570-1681, especially 1630-1632.

Scoped path persists an unconfirmed:<uuid> marker BEFORE dispatch, replaces it
with a returned job ID, waits for that job, and checkpoints the confirmed state.
A lost response retains the uncertainty marker. Retrying it does not reorder
again and cannot mark sorting published. A matching order snapshot is not used
to clear that marker. This is correct fail-closed behavior, not a retry defect.
The missing automatic escape for an unknown job is an operational reconciliation
requirement; automatically replaying it would make safety worse.

Parent path still calls reorderProducts before trackJob persists the ID. A
response lost after acceptance leaves no durable uncertainty record. The next
parent attempt can infer success from matching products/order without checking
the accepted asynchronous operation. If the visible order is still old, the
same missing marker also leaves a replay window; the diagnostic demonstrates
the premature-completion variant, not a second live mutation.

Reproduction: seed a persisted legacy collection order without explicit scoped
sort rows, make an authorized layout edit, queue parent publication; fake an
accepted asynchronous reorder whose current snapshot matches the target but
whose response is lost and whose operation is still pending. First push fails
with no remote_jobs entry. A newly queued parent push ends synced without any
job-status poll while the fake still records the operation as pending. Passed.
This fixture establishes the accepted legacy path, not how many such drafts
exist in production. New explicit sort submissions normally use scoped publish.

Impact: parent recovery can finalize or later overwrite work while an unknown
operation remains in flight. Deployment blocker: YES for the accepted parent
path unless it is explicitly excluded and persisted legacy data is verified.
Smallest correction: persist uncertainty before every parent asynchronous
mutation too; retain known job IDs and require their completion. Add a deliberate
operator reconciliation path for unknown outcomes. Neither elapsed time nor a
matching snapshot alone proves completion. Do not automatically replay.
Coverage: ScopedPublicationRecoveryTest's four cases passed, including dependent
chunks, lost response, killed worker and revoked permission. New parent diagnostic
exposes the uncovered boundary.

3. PARENT SHOP YOUR VIBE CONCURRENCY AND OPERATION-LOCK EXPIRY

Classification: CONFIRMED DEFECT. Existing parent layout/publication workflow.
Locations: app/Services/ShopYourVibeWorkflow.php:918-919,1066,1135,2259-2287;
app/Services/ShopYourVibeEditing.php:300-350; app/Jobs/PushShopYourVibe.php:20-22.

Path: parent push validates its ticket, takes a 180-second Cache::add operation
marker, and installs a before-mutation ticket validation hook. It refreshes the
marker at a few phase boundaries. The job timeout and authorization lease are
840 seconds. Long reads, batches or a slow API call can cross the 180-second
marker expiry before the next phase renewal. Another delivery can then acquire
the marker while the old ticket remains authorized. The mutation hook checks
ticket/actor/revision/expiry, but not current operation-lock ownership.

MySQL reproduction: acquire the actual parent's cache marker, expire its row,
start another PHP worker which acquires and holds a replacement marker; validate
the old ticket and invoke a fake Shopify mutation through the actual mutation
authorization hook while that second worker is alive. The old worker is still
authorized. This isolates fencing; it does not claim that a second worker already
completed a whole publication before the first.

Renewal and release additionally use separate get/put and get/forget operations;
their ownership-check race is visible in code but was not separately forced.
The 900-second scoped execution lock is a different safeguard and does not cover
the parent path. A shared cache is necessary, but does not fix lease loss.

Impact: overlapping parent workers may issue conflicting writes and checkpoints.
Deployment blocker: YES for parent publication.
Smallest correction: use an owner-aware atomic lease sized/renewed for the actual
execution budget; check/fence its current owner immediately before mutation and
checkpointing; release only by owner. Preserve ticket/permission checks as well.
Coverage: existing scoped recovery/collection-isolation tests pass. New MySQL
interleaving demonstrates the parent gap using the real cache and auth hook.

4. LAYOUT PUBLICATION WITH ANOTHER COLLECTION'S UNPUBLISHED SORTING

Classification: CONFIRMED DEFECT, but NOT an approval bypass.

and does not send their product mutations. Layout/metaobject writes proceed.

reports failure and leaves misleading pending/retry state. No unapproved sort

Smallest correction: build the final confirmation projection using the held
collection's confirmed baseline, then merge its desired order back as pending.
Continue strictly verifying every collection actually published.
Coverage: ShopYourVibeCollectionIsolationTest passes for scoped publication and
editing isolation, but did not push a layout while a separate sort was held.
New "layout publication followed by false failure" diagnostic covers that case.

5. PARENT PUSH TIMEOUT AND ABANDONED-STATE RECOVERY

Classification: CONFIRMED DEFECT in terminal-attempt cleanup; uncertainty
protection itself is intentional. Locations: app/Jobs/PushShopYourVibe.php:43-74;
app/Services/ShopYourVibeEditing.php:54-79,360 onward.

Parent failed() takes the draft row lock and checks ticket identity/revision.
It then returns if any operation marker exists, including the dead worker's own
unexpired marker. Cache expiry later performs no database transition. Normal
editing/discard is blocked by status pushing. abandonedLegacyPush intentionally
accepts only an old, unowned, checkpoint-free legacy flag with empty editing_state
and no queued work; a normal ticketed failed push cannot use that escape hatch.

Reproduction: create the matching ticketed parent in pushing state; leave its
worker marker alive; invoke the terminal failure callback; advance 181 seconds.
The marker is gone but the draft is still pushing. Passed. A final attempt killed
soon after a marker renewal, followed by failed(), is a realistic trigger. An
earlier failed attempt may later redeliver and eventually clean up, so "every
timeout permanently sticks" would be an overstatement.

Impact: parent workspace can remain unusable after the final worker exits.
Deployment blocker: YES for reliable parent recovery.
Smallest correction: record owner-aware terminal failure/recovery intent and
reconcile it once the worker is fenced out. Keep known jobs/checkpoints and all
desired changes. Do not treat a missing marker as proof of Shopify completion
or discard an uncertain mutation to make the UI editable.
Coverage: scoped killed-worker and revoked-permission recovery passes; it does
not cover this parent branch. New parent failure callback diagnostic does.

6. BUNDLE INVENTORY APPROVAL QUANTITY PROPAGATION

job, distinguish it from automatic stack sellability intent, and confirm that

approval. Do not reinterpret all stack quantities or change tracking globally.
Coverage: existing approval tests check local approval state; existing on-hand

8. SUPPLIER RECEIPT DELTA IDEMPOTENCY AND AMBIGUOUS RETRIES

Classification: same-receipt fail-closed retry is INTENTIONAL and effective;
replacement receipt while uncertainty remains is a CONFIRMED DEFECT.
Locations: app/Jobs/ProcessSupplierReceiptJob.php:31-85;
app/Services/Procurement/SupplierReceiptService.php:23-29,170-176,195;
app/Models/ProcurementSupplierOrderLine.php:24-34;
app/Services/Shopify/ShopifyInventoryAdjustmentService.php:158-204.

Path: receipt creation deduplicates its request key and locks the PO line for
quantity reservation. Processing conditionally persists started_at before the
delta call. Only one claimant wins. If the response is lost after acceptance,
the row becomes manual_review; redelivery sees started_at and does not send the
delta again. A succeeded receipt skips the delta during postprocessing retries.
The receipt delta lacks a provider idempotency directive, but that fact alone
does not establish automatic double receiving with this claim/quarantine guard.

Tests: direct handler with fake increaseAvailable throwing after acceptance is
called twice; the fake receives increaseAvailable exactly once and the receipt
stays manual_review. Passed. Real MySQL competing conditional claims block on
the receipt row and, after the first commits its marker, the other updates zero
rows. One claimant wins. No real stock was received.

Separate failure: manual_review is excluded from reserved quantities. The line's
displayed outstanding quantity also subtracts only succeeded receipts. A user or
CSV can submit a new key for the same physical delivery while the old delta may
already have applied. Reproduction: PO for five; receipt five with started marker
and manual_review; create another five with a new key. Both rows exist, total
receipt quantity ten against an order for five. Passed. This is not automatic
replay of the same receipt, but it bypasses the uncertainty quarantine by renewal.

Impact: double receiving and inflated purchasable stock. Deployment blocker: YES
for replacement receiving while an outcome is unresolved.
Smallest correction: reserve uncertain quantities or block new receipts for the
affected line until deliberate reconciliation. Preserve same-key deduplication,
atomic claim and postprocessing-only retry. Never clear started_at and replay
the delta merely because the quantity looks plausible. Provider idempotency, if
added, requires verified API support and a stable immutable receipt key.
Coverage: ProcurementSupplierOrderWorkflowTest covers same-key and over-receipt
validation; new handler quarantine and replacement-key tests plus MySQL claim
test cover the important distinction.
