INDEPENDENT AUDIT: COMPONENT-TO-STACK IMAGE SYNCHRONIZATION
20 November 2026, Africa/Johannesburg

VERDICT: NOT READY FOR PRODUCTION ACTIVATION.
Read-only or deliberately isolated diagnostic staging is appropriate. Do not activate
automatic Shopify publication or combine legacy propagation with the new workflow.

The actual working tree was inspected independently, including all new services, jobs,
observers, commands, operator page, configuration, scheduler, migration and tests. Passing
tests and previous implementation reports were not treated as correctness evidence.
No application source was changed. Temporary diagnostic tests/harnesses were removed after
archiving their reproducible source as text under storage/logs. No deployment, feature-flag
change, commit, production data change or live Shopify mutation was performed.

READINESS BY WORKFLOW
Manual CMS stack rebuilding: NOT READY for the complete stated workflow. Simple initial
copying now works without component approval or Shopify publication, with all automatic
flags disabled. Replacement/removal, shared provenance and occupied-position reordering
still have confirmed defects.
Automatic local rebuilding: NOT READY. Normal alt/import editing paths bypass the event
hooks, concurrent staging is not serialized, and queued jobs ignore disabled flags.
Automatic blind Shopify publication: NOT READY. Retirement is not executed by the new
planner; authorization/version, confirmation, cursor recovery and flag handling are unsafe.
Legacy baseline initialization: NOT READY. --publish can report baseline_verified without
one Shopify read; tag-only stacks are excluded.
Publication reminders: NOT READY. Nominal timing works, but real edit paths are missed,
resolved/reopened issues are suppressed, and concurrent delivery can send duplicates.

CONFIRMED FINDINGS: 2 CRITICAL, 10 HIGH, 5 MEDIUM, 1 LOW

C1 CRITICAL - Legacy removal bypasses the inactive/draft stack guard.
References: app/Services/ComponentStackPropagation.php:220,272,1223;
app/Services/ProductShopifyUpdater.php:1141.
Path: synchronizeTask handles purpose=remove and returns before the newly added active
stack guard. removeInheritedComponent calls remote retirement for a draft stack.
Reproduction: stage one inherited photograph, attach its independent MediaImage, make the
stack draft, remove the member, then execute a legacy remove task. The diagnostic observes
one fileUpdate association-removal request and the CMS copy becomes local_deleted while
the stack remains draft. Expected: local-only reconciliation and zero Shopify mutations.
Correction: enforce current active status and authorization on every destructive entry
point and again at mutation boundaries, including removal tasks and shared helpers.
Coverage: existing draft test exercises the new synchronizer, not legacy removal. The
diagnostic 'legacy removal task deleting a draft stacks association' detects this.

C2 CRITICAL - Legacy primary propagation retires another CURRENT component photograph.
References: app/Services/ComponentStackPropagation.php:401,458,760-817 (retireOlderInherited).
Path: new staging copies ALL component photographs, but legacy retirement still selects
all other inherited images by component_product_id and a different asset. It assumes every
other asset is an obsolete generation of the primary image, including current secondary
photographs introduced by the new local rebuild.
Reproduction: component has current A at position 1 and B at position 2; both stack copies
are independently attached. Execute confirmed primary-A legacy publication with both
mechanisms enabled. B's association is removed and its CMS copy retired although source B
is still active/current. Expected: retain both current desired photographs.
Correction: make the mechanisms mutually exclusive until retirement operates against the
complete desired gallery and exact source-image/generation identity, not component ID.
Coverage: old retirement tests use one selected component photograph; new tests copy all
photographs locally without executing legacy retirement. The diagnostic reproduces the
actual removal request with different original bytes for A and B.

H1 HIGH - Version and authorization capture bypass actual approval snapshots/edit paths.
References: app/Observers/ImageObserver.php:50,422;

app/Services/ShopifyImageImportService.php:479-565;

Reproductions: A -> B -> A through markPendingReview leaves alt_text_version=1 and reuses

Coverage: current new tests seed versions manually or call ordinary save; they do not

H4 HIGH - Ledger and baseline claim verification without the required remote evidence.
References: app/Services/StackImageSync.php:196-253,428-454,488-495,506-539,571-579;

H5 HIGH - Existing published inherited descriptions cannot follow new source alt text;
independent overrides are incorrectly planned as source updates.
References: app/Services/ComponentStackPropagation.php:708-739;
app/Services/StackImageSync.php:229-239,530-546;
app/Services/ImageAltTextBackfillService.php:265-288.

publishInheritedCopy, which rejects a copy whose saved sentence differs from the newly
approved source. Conversely, plan ignores alt_inheritance_mode and compares intentional
independent stack overrides against the source sentence, causing perpetual alt plans or

Reproductions: published copy A, source changed to B, rebuild leaves A; publication's
sentence-equality gate rejects it. A correct independent override is planned in alt_only.

independent and can reach a verified/no-change result.
Correction: use one mode-aware authorized alt target in staging, planning, delivery and
receipts. Preserve old text/history without freezing component-following copies forever.
Coverage: new edit test uses an unapproved copy; independent-alt tests exercise another
publisher rather than this new planner/executor combination.

H6 HIGH - Concurrent local rebuilds are not serialized per destination stack.
References: app/Services/StackImageSync.php:45-57,167;
app/Services/ComponentStackPropagation.php:401,533-565;
app/Jobs/RebuildDependentStackImagesJob.php:26;
app/Filament/Pages/StackImageSyncStatus.php:63.
Path: those entry points call stageStack without a stack mutex or row transaction. The
local-job cache key is per component, so two components feeding the same stack do not
exclude each other. Staging performs select-then-insert and can retire the competing row.
Real MySQL reproduction: two separate actual stageStack workers both observe no row, then
both insert. Expected total=1/active=1; observed total=2/active=1 on two runs. The source
photograph was unchanged. This is not a SQLite locking inference.
Correction: serialize the entire local desired-gallery operation per stack using the
existing non-expiring session-mutex contract, with fresh state and transactional writes.
Coverage: existing coalescing tests fake job dispatch and run serially; legacy MySQL
generation tests do not exercise this new staging path.

POSITIVE / VERIFIED LIMITS
Simple local creation copies all readable current source photographs with separate CMS
rows and no component Shopify/approval requirement. Managed asset/provenance data is stored,
stack-owned images are retained, and missing files are reported/protected from automatic
local removal. Basic repeated staging reuses existing active assets serially. Existing
per-image upload claims, READY/SHA checks and low-level session mutexes still provide useful
defenses, but do not cover the new whole-stack orchestration. Legacy ambiguous ownership is
not silently classified by the new baseline command. Feature defaults are all false.
The reminder query implements a 90-minute cutoff, its scheduler runs every 15 minutes, and
nominal follow-up is 24 hours after initial acceptance. Recipient configuration is
services.slack.missing_alt_recipient_email / MISSING_ALT_RECIPIENT_EMAIL, defaulting to
nick@leighavenue.co.za; the rendered mail includes SKU-filter instructions. These timing and
format checks do not establish complete issue detection or duplicate-free delivery.

REQUIRED CORRECTIONS / RELEASE PRECAUTIONS
Keep all three automatic flags false. Fix C1/C2 before any mixed legacy/new publication
test outside a disposable development store. Establish one desired-state/approval contract
across real edit services, local staging, planner, executor and receipt writer. Execute
retirement through the existing guarded machinery. Serialize destination-stack staging,
recover cursor failures durably, preserve operator decisions on no-op rebuilds, and repair
mode-aware alt propagation. Add the missing execution-path regression cases above, not
just extra planner assertions. Retain the new metadata on application rollback.
No broad rewrite is justified by this audit; the defects identify specific missing gates,
state transitions and executor branches in the current architecture.

After corrections: apply/retry the new migration on a disposable production-shaped MySQL
copy, stop old workers during deployment, restart matching-version workers, and verify
effective cached flags. Test whole-stack parallel jobs, worker termination/connection loss,
stale approval interleavings, lease expiry and coalesced arrivals using actual new jobs.
In an authorized development store test full multi-photo publish, alt-only changes,
replacements, removal/re-add/removal, variant reassignment, external media deletion/alt
drift, delayed readiness and lost responses. Verify exact separate component/stack media
IDs and shared-file behavior with complete pagination and fresh read-backs. Test legacy
and new flags together only after their destructive conflict is fixed, or enforce mutual
exclusion. Verify reminder concurrency, acceptance uncertainty, resolution and reopening.
Do not infer production readiness from SQLite mocks or from the reproduced MySQL tests.
