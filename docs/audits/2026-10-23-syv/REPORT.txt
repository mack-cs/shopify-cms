Independent technical audit: Shop Your Vibe
23 October 2026 â€” local working tree at 6f59d03, including existing uncommitted changes

OVERALL VERDICT: NOT PRODUCTION-READY against the requirements in the audit brief.

The editor has useful performance and reliability improvements, but successful tests conceal important gaps. A deleted linked collection can have its requested order silently skipped while the whole draft becomes synced. Missing mappings remain active. Refresh can mirror historical unavailable data over newly retrieved product data. Local draft tags can place a real Shopify product into a supposedly verified membership snapshot without Shopify returning that membership. These are release blockers.

Scope and safety
---------------
No Shopify mutation, deployment, production data update, real-record deactivation, Git commit, or Git push was performed. Application code and the user's pre-existing edits were left unchanged. Temporary independent test files were moved into this audit folder as inert .php.txt evidence after execution. Only audit artifacts were added.

Production was not accessed. No production Supervisor configuration, deployed source hash, worker process, failed_jobs table, queue depth, shared-cache behavior, production database, or authenticated production browser session was verified. The claim that a new production worker is running remains unverified. This report is not a production acceptance certificate.

Evidence labels:
C = direct code inspection; T = executed isolated PHP/Livewire test; J = executed Node harness using the actual extracted editor JavaScript; D = official Shopify documentation. No findings are represented as live browser or production observations.

Reviewed the working-tree diff and relevant recent loading/sorting commits, SYV page, view, CSS, workflow, jobs, mapping model/service, Shopify adapter and actual gateway binding, product mirror, complementary counts, sibling handling, shared product updater, queue/cache configuration, and tests. AppServiceProvider binds ShopifyGraphqlGateway to ShopifyApiClient, not the separate Shopify/ShopifyGraphqlClient class.

1. Verified improvements
------------------------
* Cached complete collection opening and local drag/numeric workflow actions require no Shopify calls in the tested fixtures. Product arrays stay out of public Livewire state. [T,C]
* Missing product arrays trigger background hydration. Duplicate ordinary Manage requests queue one hydration job in the existing tests. Confirmed empty product arrays render as loaded. [T,C]
* Retrieval is accumulated in memory before a draft snapshot update. Exceptions during ordinary retrieval preserve the previous draft. Revision checks protect pending local draft edits in tested hydration races. [T,C]
* Completed hydration can advance through ready_to_render into rendered products through the Livewire status path. Old progress does not override a complete loaded parent snapshot in those tests. [T,C]
* Refresh now distinguishes terminal refresh states even when products are already displayed. Existing tests exercise failure banners, Retry, keeping products visible, missing progress, and stopping the rendered spinner. This addresses the prior Bracelets symptom at the server/Livewire level; real browser behavior and worker restarts remain unverified. [T,C]
* Refresh can preserve historical data for a missing linked collection and continue retrieving valid collections. This is only partially correct: see F1, F2 and F7. [T,C]
* Full-list local reorder validation rejects missing/duplicate members and out-of-range integer positions. Page-session epochs allow a reloaded editor to start again at epoch 1, and reject older requests within that session. Pending revision conflicts are checked in the workflow. [T,C]
* Push preflights changed existing collections against current Shopify membership/order, validates GraphQL mutation userErrors, waits for asynchronous jobs, checkpoints work, and reads back results. Ordinary failures retain pending state. These safeguards do not close all failure paths below. [T,C]
* Complementary count batching preserves linked NewProductDraft -> catalogue primary row -> metafield precedence. An existing empty linked draft intentionally wins with zero; it is not replaced with a lower-priority source. Missing sibling-cache data is explicitly presented as Not loaded. Movement classification uses the latest completed movement run by SKU. [C,T]

F1 â€” HIGH: Skipped linked-collection push reported as fully synced. [C,T]
Location: app/Services/ShopYourVibeWorkflow.php:635 push(), especially the missing-collection catch around line 683; :889 confirmedState().
Root cause: both preflight and final collection confirmation swallow ShopYourVibeCollectionUnavailableException for linked collections. They neither retain a failed operation nor require a verified result for that requested change.
Reproduce: load linked collection 2; save a reversed local order; make fake Shopify return null for that collection; queue and execute push.

F4 â€” HIGH: Stale editor can queue another editor's unreviewed revision. [C,T]
Location: app/Filament/Pages/ShopYourVibe.php:1423 queueDraftPush(), :1357 reviewPush(), :1387 pushChanges(); ShopYourVibeWorkflow::queue():438.
Root cause: queueDraftPush() silently adopts the latest pending/failed revision before queueing. There is no persisted binding between a reviewed revision and the queued operation.
Reproduce: open two Livewire editors on the same synced draft. Editor B reorders products. Editor A, still on the old revision, invokes pushChanges().
Expected: stale A is rejected and must review B's actual saved revision before approving it.
Actual: A's revision is silently advanced and B's order is queued. The independent test faked dispatch; nothing was pushed externally.
Correction: capture and strictly compare the reviewed revision when queueing. A failed-attempt retry must verify that desired content still equals the content previously reviewed, rather than accepting arbitrary newer pending state.
Approval limitation: this SYV path has an access guard and a review modal, not a persisted two-person approval gate. Do not claim New Products or Collection Approval is automatically enforced here. queueImagePush() also queues the entire pending draft when an image changes, so a prior local order can travel with an image save without the ordinary order review. Preserve intended approval requirements explicitly.

F5 â€” HIGH: Refresh uniqueness is deliberately released before each dispatch. [C,T]
Location: app/Filament/Pages/ShopYourVibe.php:333 refreshDraft(); app/Jobs/RefreshShopYourVibeDraft.php:45 releaseUniqueLock().
Root cause: refreshDraft() unconditionally releases the unique-job lock before dispatch, even if another refresh is queued or running.
Reproduce: with a real isolated database queue and after_commit disabled for the test transaction, call refreshDraft() twice on the same editor.
Expected: one active refresh for that draft, with one attempt's progress.
Actual: two queue rows. Both jobs also use the same collection progress key and can race to overwrite running/success/skipped/failure states.
Correction: keep uniqueness for live jobs. Recover only a proven expired attempt; use an attempt identifier and heartbeat. Forced hydration retry similarly must not release the lock of a genuinely running job.
This duplicate-refresh route is introduced by the uncommitted releaseUniqueLock call.

F6 â€” HIGH: Long push concurrency is not protected for the full operation. [C; race not executed]
Location: ShopYourVibeWorkflow::push():635, holdOperationLock():1633, releaseOperationLock():1649; app/Jobs/PushShopYourVibe.php.
Root cause: operation exclusion uses Cache::add with a 180-second lease while the job timeout is 840 seconds. It is renewed only at a few phase boundaries. A slow preflight or collection/job loop can outlive the lease. Draft status is read before lock acquisition, not reread under the acquired lock. Locking is by parent even when different parents share a linked collection.
Reproduce: delay Shopify pages beyond the lease; enqueue Retry / Check Push or operate on a second parent sharing the same linked collection. Allow another worker to acquire the expired lease.
Expected: at most one current revision writes any target; stale jobs exit after acquiring the lock.
Actual from control flow: a second operation may enter with a stale draft object, and a shared linked collection has no target-level exclusion. Exactly-once mutation delivery cannot be guaranteed, especially if a remote response is lost before checkpointing.
Correction: use an owner-safe lock with a lease covering the bounded operation or reliable renewal, reread status/revision after acquisition, and serialize shared collection targets. Preserve readback/checkpoint-based retry rather than promising exactly-once network execution.

F7 â€” HIGH: Preserved unavailable data overwrites fresh catalogue values during refresh. [C,T]
Location: ShopYourVibeWorkflow::refresh():207, pullState():1544; app/Services/ShopYourVibeProductMirror.php:24 mirrorFromDraftState(), :73 mergeProductCards().

3. Shopify source of truth and entity lifecycle
----------------------------------------------
Normal hydration reads Shopify collection/product IDs and ordering. The normal draft push uses the saved desired list, checks remote changes, computes sequential zero-based moves, batches at 250, and confirms jobs. Drag itself writes only locally.

Source-of-truth failures are F1/F2/F3/F7/F8. Missing-product filtering in productsMissingFromShopify() avoids reintroducing baseline products that the current collection no longer returns, but it does not distinguish product deletion from removal/movement between collections and does not deactivate a local product/assignment record. It also removes those products from snapshot/desired during push, without a distinct historical tombstone model. Preserve history and make the event explicit.

Missing metafield is interpreted as an empty reference list, which is reasonable only after a valid successful response. The gateway normally throws HTTP and GraphQL errors, including permission errors. However, ShopifyApiClient::graphql() returns [] when data is missing, and collection() uses null-coalescing for both a missing collection key and an explicit null. An invalid success body can therefore be classified like a missing collection. Require valid response shape before declaring authoritative absence. The unavailable error text currently asserts the request succeeded and was not access denied more confidently than the adapter proves.

Pagination failures throwing an exception do not publish the in-memory partial list. Missing/repeated cursor safeguards and structural/count verification need improvement. A repeated nonempty cursor is not detected and can keep reading until timeout. A live collection changing during multi-page retrieval is also not an atomic Shopify snapshot; a consistency check or retry policy is needed before relying on it as a push baseline.

An existing is_active mapping field already provides the smallest safe deactivation mechanism. Do not add a migration by default. Parent collection absence currently fails refresh rather than deactivating all associated active mappings. Linked card/metaobject absence generally fails parent parsing; no unified unavailable entity lifecycle covers all these entity types.

4. Hydration, refresh, and loading architecture
-----------------------------------------------
Prefer Option A: complete background hydration, page-level progress, and atomic publication of a verified completed snapshot. It is already close to this architecture and has the smallest correction surface.

Option A: approximately ceil(N/100) product-page queries per collection (at least one for zero products), plus definition/parent/card/link queries; cache progress writes per page; a final draft publication. Current refresh additionally mirrors catalogue rows per product, so its database work is substantially larger than just one snapshot write.

Option B: similar minimum retrieval queries, but needs durable cursors, staging rows or generation buffers, idempotent page ingestion, duplicate checks, recovery state, partial-render rules, and more database/UI updates. It can show the first page earlier but must still disable global ordering and push until the entire list is verified. It does not inherently reduce Shopify cost. There is no measured evidence here that warrants that added complexity.

Current state is a mixture of ephemeral queued/running/success/failed/skipped cache entries, ready_to_render/loaded presentation state, products-array presence, and client booleans. Progress is keyed by collection, not job attempt. The 600-second progress expiry is shorter than the 840-second job timeout and excludes a busy queue's wait time. Cache expiry can be shown as refresh failure while a valid job is still executing. Multiple attempts can overwrite each other's progress; F5 makes that reachable without a worker restart.

Pending drafts are protected by ordinary edit revision checks and pending guards, but no separate pending-approval state is modeled in ShopYourVibeDraft. Refresh mirrors shared product/draft data outside the final draft transaction. It therefore cannot be described as protecting every related pending product approval record solely because the SYV JSON remains unchanged.

5. Sorting, push, approvals, and retries
----------------------------------------
The current browser numeric control and pointer drag both submit a complete DOM order through queueProductOrder() -> page reorderProducts() -> workflow edit('reorder_products'). The older server moveProductToPosition() also delegates to that workflow operation. Search blocks both browser drag start and numeric commit while a query is active. Local stored order is validated as a permutation and normal responses reconcile IDs from the database. Epoch and revision safeguards are useful; F4/F6/F10/F11 are the important exceptions.

Shopify API capability check: collectionReorderProducts requires sortOrder=MANUAL, returns an asynchronous job, accepts up to 250 sequential moves, and uses zero-based positions. The implementation's move format/batching agrees. Automated rule-based membership is a separate concern from manual sort order; do not ban sorting merely because ruleSet is non-null. The code correctly blocks direct membership edits for rule-based collections. manualSortingSupported() uses a permissive OR that can override an explicit manual_supported=false whenever sort is not UNSUPPORTED; make that capability check fail closed for unavailable/unsupported targets.

Official source: https://shopify.dev/docs/api/admin-graphql/2026-01/mutations/collectionReorderProducts

Ordinary userErrors/GraphQL errors are handled, and successful requested collections are read back. waitForJob() waits only about five seconds of sleeps plus request time, so genuinely long Shopify jobs become pending failures requiring retry; remote_jobs supports later confirmation. Push catches most exceptions and updates failed rather than rethrowing. Consequently the queue's job retry count does not automatically retry those failures; it is primarily a UI retry workflow. Retry / Check Push can dispatch duplicate jobs and relies on the operation lock, with the limitations in F6.

No real Shopify mutation was executed to validate remote capability or idempotency. Exactly-once submission is not established. A lost mutation response before storing its remote job ID is an ambiguous result. Re-read remote state before repeating such work.

7. Product cards and presentation
---------------------------------
CSS places Sold Out top-right of the thumbnail, Low Stock bottom-left, Movement bottom-right, and Position to the right of card tools. Position is a normal number input and drag has an aria-label and a visible icon. Responsive CSS exists. Desktop/mobile visual layout and drag accessibility were inspected in source only, not certified in a rendered browser.

Sibling absent cache is distinguished from a loaded empty cache. Complementary empty-draft precedence is retained. Movement labels are sourced from completed reports, not invented from cached inventory. Materials/colour/finish and tags have both Shopify snapshot and catalogue/mirror paths; F7 means the displayed and catalogue values can diverge. ProductMirror ignores null/empty metafield entries when normalizing/mirroring, so confirmed removal of a remote metafield can leave old catalogue/draft values rather than clear them. Treat explicit removal differently from unavailable retrieval, following the existing business policy on safe clears.
