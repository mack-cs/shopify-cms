ORIGINAL FAILURES AND CORRECTED BEHAVIOR

1. Mixed order batch: valid FIX-1 and invalid SKU/quantity.
   Before: confirm rejected the mixed batch; no partial-acceptance API existed.
   Initial regression failed with unsupported acceptValidRows argument.
   Now: preview persists no purchase order. Confirmation without explicit partial
   consent fails. Explicit consent saves exactly the valid line; invalid raw
   values, original row number and all explanations remain downloadable.

2. Receipt batch: two quantities of 3 against an order of 5.
   Before: preview incorrectly marked both rows valid (valid_count=2).
   Now: upload and paste mark both rows rejected with the combined quantity and
   the actual available balance. Pending/processing receipts reserve capacity.
   A manual_review receipt quarantines further receiving for that order line.

3. Draft not created/synchronized in Shopify.
   Before: rejected without the necessary Shopify mapping explanation.
   Now: preview rejects before staging/mutation and explains that Shopify product,
   variant and inventory-item mappings must be synchronized before receiving.
   Purchase-order planning for an unmapped ordinary CMS draft remains possible.

4. Approved tracked 1-bead receipt, active and unlisted source variants.
   An additional before-change job reproduction used the real HTTP guard with
   fake Shopify. Both variants failed with "Engraved bead Shopify mutations are
   disabled until both inventory-write and store-contract flags are enabled."
   No mutation reached fake HTTP. This established the actual guard conflict;
   the initial missing authorizePush-method failures alone were not sufficient.
   Now: the approved, explicitly authorized source receives exactly one delta,
   with both automation flags false. Duplicate job delivery does not send another
   delta. Generic GraphQL, additional mutations and REST writes remain blocked.

IMPORT EXECUTION AND TRANSACTIONS

SupplierImportPreview parses both transports and retains raw values, headings,
original row identifiers and blank-row positions. Validation explanations are
shared. Duplicate order/SKU rows identify the earlier row. Existing PO/SKU rows
name the actual order and SKU, say "already recorded", promise no quantity
overwrite, and direct amendments to the existing authorized Amend Order Line
action. Unrelated valid rows can be explicitly accepted.

Filament upload/paste actions now validate then open Review Supplier Import.
Valid/rejected tables contain every row, including errors after row 10. Mixed
batches require a consent checkbox. Receipt confirmation stages only; the user
must separately authorize Push Received To Shopify. Rejected downloads require
an active inventory-authorized user, contain original cells (including extra
malformed columns), Original Row, and Error Reason. Correction exports omit
previously accepted rows; corrected files can be re-uploaded. Existing completed
file hashes and row idempotency keys remain in use.

Confirmation locks the batch, affected existing orders and order lines, then
revalidates before writing. Accepted rows persist together in one transaction.
If validity/reasons changed after preview, only the revised preview commits;
the user must review again and no accepted business rows are saved in that call.
Receipt quantities are summed per order/SKU before staging. The existing line
lock and service-level capacity check remain a second enforcement boundary.

Confirmed outstanding = ordered minus succeeded receipts. Staged is pending plus
processing; uncertain is manual_review. Available to receive subtracts staged
from confirmed outstanding, and is zero while an uncertain receipt exists. WIP
and confirmed-inventory formulas were not changed.

RECEIVING ELIGIBILITY AND AUTHORIZATION

A. Published tracked 1-bead: allowed only if the existing approved source contract
   validates the family, current IDs/SKU/tracking/location and mapping/version.
B. Unlisted tracked 1-bead: same conditions; unlisted status alone is not rejection.
C. Eligible mapped ordinary draft: resolves to its unique synchronized variant
   and product/variant/item IDs. A CMS draft's Shopify product ID constrains the
   match when present. Binding occurs only at accepted staging, not preview.
   Draft/unpublished status is preserved. Existing unique-SKU linking when a
   previously unmapped draft later gains a synchronized variant is retained.
D. Unmapped draft: actionable rejection before any Shopify mutation.

All receiving requires a non-stack product, supported product status, all three
Shopify identities, and tracked=true. 2/3/4-bead members cannot become independent
receiving sources, even through the direct supplier-order service. The source
contract is reused, not replaced by tags or a new business approval mechanism.

Explicit push approval records actor, quantity, product/variant/item/location,
and approved-source mapping hash/version on the receipt. Current inventory
permission is rechecked in the worker. Mapping/location/quantity drift invalidates
the authorization. A bead job without this authorization cannot use the exception.
The worker refreshes bead inventory before attempting the delta; missing/false
tracking blocks it before recording a started Shopify attempt.

SupplierReceiptMutationAuthorization is scoped and cleared in finally. It permits
only the exact existing supplier-receipt GraphQL mutation and exact one-change
payload: name=available, reason=received, approved item/location/positive receipt
quantity, receipt reference and stable idempotency key. The receipt must have its
durable processing/start marker. Changing any identity, amount, reference, key,
or query does not pass the guard. There is no REST or generic mutation exemption.

The pre-existing atomic attempt claim, dedicated inventory-receipts queue,
single-attempt mutation behavior, response acknowledgement and ambiguous-outcome
quarantine remain intact. Uncertain mutations are never automatically replayed.
Only Shopify adjustment-group confirmation sets succeeded. inventory_after starts
null and is populated from a confirmed refresh, not a predicted local addition.
If post-receipt refresh/summary work fails, the receipt stays succeeded with the
"Received in Shopify; stock summary needs updating" label. A retry does the
post-processing without another stock delta.

previously approved families only in disposable databases.
